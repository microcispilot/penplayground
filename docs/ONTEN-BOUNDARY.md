# The Onten boundary — what is Onten's, what is Pen's, and what drifted

Audited 2026-09-18 by reading every file named below, line by line. Every verdict
cites where the code actually is, not where it ought to be.

## The one sentence this document exists to protect

> Onten is the SDK that compiles and prepares the data we give it, and gives us
> the answer context for any question in **sub 20 ms**. Like a human brain: give
> it information, and later — with no re-thinking — it hands it straight back.
> We do not have Onten yet, so we **mock** those two abilities. Simulated content
> is fine until the real SDK lands. The contract is not.

That is the owner's framing, and it decides every row below. Two questions settle
any case:

1. **Would the real Onten do this?** Then it lives behind `packages/onten` — and
   nowhere else, ever.
2. **Is this generated by us, about us, or about our learners?** Then it is Pen's
   and it stays out of `packages/onten`, so the mock can be deleted whole when
   the SDK arrives.

Corroborating primary sources, all in this repo:
`onten-answercontext-examples/01-memo-hit-repeated-question.yaml` ("the search
already happened, correctly, **inside 20 ms**"; "the memo never caches an answer,
it caches the SELECTION"), `02-personalized-misconception.yaml` (the shared memo
key is a bounded `selectionBand`, never learner state), `03-progressive-first-use.yaml`
(status `partial` over a false `sufficient`; measurement belongs in the run
manifest, never in the AnswerContext).

---

## The table

**Onten's** — must live behind the mock interface, and does.
**Pen's** — ours forever; the real SDK will not take it.
**Drift** — we implemented, or contaminated, something Onten owns. All drift
found in this audit is listed with what was done about it.

## Drift knowingly retained (one item)

**Cross-language canonical-title resolution stays in `services/api/src/language.ts`.**

What it is: a non-English request ("می‌خواهم سوئیفت یاد بگیرم") gets one cached
model call that produces the English topic title, so it keys the same pack as an
English learner's request. In a real Onten that is `resolveTopic` doing its job —
descriptor containment is semantic, and the registry is language-aware by
contract. Our mock's registry is lexical, so the host pre-translates to make the
lexical mock work. That is, honestly, us doing Onten's job.

It was **not** moved, for two reasons that are about architecture, not
convenience:

1. `packages/onten` depends on `contracts` and nothing else
   (`docs/CAPABILITY-MAP.md`). Moving this in would make the Onten mock depend on
   `@pen/llm`, invert the dependency arrow, and mean the package that must be
   deletable in one commit no longer is.
2. The module whose whole contract is "sub 20 ms, no re-thinking" would then
   contain a multi-second network call to a language model. Even on a path the
   budget does not cover (`resolveTopic`, not `query`), that is the wrong thing
   to put inside that boundary.

So it is recorded here rather than hidden. **When the real SDK lands, delete
`TopicIntake`'s translation call and its cache and pass the learner's raw text
and language to `resolveTopic`.** Language identification (`detectLanguage`,
`detectSpokenLanguage`) and `cleanTitle` stay — those are the microphone's, not
the registry's.

## Known mock limitations (simulated, and said out loud)

Per the owner: inaccurate simulated content is fine; a silently unkept contract
is not. These are the places the mock is thinner than the real thing.

1. **The qualification gate does not run the evaluation set.**
   `packages/onten/src/progressive.ts:86` checks that a development set and a
   negative set are *present* and non-empty. Onten's gate would run them and
   refuse the pack on a false-sufficient. `qualifiedOn` is therefore reported as
   `'not_qualified'` (`runtime.ts:689`) — the mock never claims a qualification
   it did not earn. Making the gate execute its own eval set is the highest-value
   next step for mock fidelity.
2. **Topic resolution is lexical, not semantic.** A reworded request finds the
   right pack but returns `partial` rather than `hit`
   (`packages/onten/test/memory.test.ts` pins exactly this). An honest `partial`
   is the correct failure direction; a wrong `hit` would not be.
3. **`resolveTopic` rebuilds a small index over pack titles on every miss**
   (`packages/onten/src/registry.ts:94`). It is off the 20 ms path — once per
   session, not once per turn — but it is linear in the number of packs and will
   want the same treatment as the query path before the catalogue gets large.
4. **No dense/embedding retrieval, no pack layering.** `denseEncoderUsed` is
   always `false`, and every pack is `shared_public_base`; tenant, audience and
   user overlays (PACK-LAYERING-01) are typed but never produced. Nothing in the
   product depends on them yet.
5. **No typed or derived facts.** `QueryInput.facts` is always `[]`
   (`packages/session-engine/src/room.ts:1052`), so `derivedFacts` is always
   empty. The curriculum-position reasoning in example 01 has no analogue here.
6. **`getPack` hands the host the whole `Pack`**, units and sources included, and
   the room reads `pack.units.map(u => u.title)` to plan a lesson
   (`packages/session-engine/src/room.ts:674`). That is *through* the Onten
   interface, so it is not drift — but the interface is wider than the host's
   need. A narrow `outline(packId)` would be the tighter seam.
7. **A question wrapped in enough conversational noise settles at `partial`.**
   Sufficiency is the fraction of the learner's content words the evidence
   covers (`runtime.ts:501`), and "sorry, Priya, one sec" are content words the
   corpus cannot cover. The *selection* is now immune to this — words the corpus
   knows are ranked ahead of words it does not, which is what stops four filler
   words evicting the four that matter (`runtime.ts:407`, pinned by
   `memory.test.ts`) — but the score still dilutes. Deliberately not tuned away:
   scoring only the words the corpus happens to know would let "what temperature
   does a mortgage need" score 1.0 against a kiln pack, and a false `sufficient`
   is the worst failure in the system while a cautious `partial` is the mildest.
8. **`QueryInput.consequential` is never read.** A consequential request is held
   to exactly the same bar as a casual one;
   `mayAuthorizeConsequentialDecision` follows `status === 'sufficient'` alone
   (`runtime.ts:689` region). The host never sets it true today.
9. **A missing pack is reported but not acted on.** `configure` now returns
   `false` when a requested pack id was not in the store (`runtime.ts:165`), so
   the condition is no longer silent — but the room ignores the return value and
   would teach from an empty index.
10. **Cite-only references are collected and dropped.** The corpus builder gathers
   `Reference[]` for sources it may cite but not ingest
   (`packages/knowledge/src/builder.ts:467`); `KnowledgeAcquirer` does not carry
   them to the room, so nothing ever shows them.

## The rule, in one line

**Never implement an Onten capability outside `packages/onten`, and never put a
Pen capability inside it.** If you are about to index, rank, select, score,
chunk, or decide what evidence answers a question — stop: that is Onten's, and
it goes behind the interface. If you are about to store something a model
generated for us — stop: that is ours, and it goes anywhere but there.
